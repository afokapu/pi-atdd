# Blind evaluation rubric

Freeze this rubric and the hidden tests before inspecting any coder result. Evaluate only the task and the base's public contract; do not reward agreement with the private reference's implementation choices.

## Running and interpreting evidence

```
node run-hidden.mjs <resultTreeDir> <outDir>
```

The input is never modified. Outputs are `hidden-result.json`, `hidden.log`, a per-run store-call record, and a retained `.hidden-run-*` working copy. Use a separate output directory, not inside the submitted tree. The runner has a 180-second test-process timeout and a fixed catalog: an import/syntax failure produces 33 counted failures, not zero tests. All 33 cases count, so `summary.pass/fail` and `countedPass/countedTotal` describe the same suite. A timed-out run earns no counted passes; inspect its log before attributing a hang to the implementation rather than the environment.

There are **33 counted cases**: T-ORDER 4, T-LOTS 2, T-IDEM 6, T-RACE 4, T-REVERSAL 4, T-AUTH 3, T-PENDING 2, T-CLOCK 2, T-FAIL 3, T-EFF 3. There are no informational cases. The v1 basics remain, with stronger yielding races, stored-result/ownership/concurrent idempotency, mixed-expiry repeated reversal, failure atomicity, and counted efficiency comparisons.

Quote matching ignores case, naming suffixes and nesting, preferring applied amounts over balances/requested values. All amounts are integer cents (a point also equals one cent). Any 4xx is accepted for a business rejection; missing session requires 401, ownership requires 403 or 404. Both `deps.now` and the system Date are controlled; asynchronous store timers remain real. Rejection-only tests have successful positive controls, so an unimplemented route cannot pass them.

Do not deduct for unspecified policy: a sequential second redemption with a fresh key, insufficient balance (reject versus partial fulfilment), key scope across unrelated orders, replay after cancellation, persistence across process restarts, equal-expiry tie-breaking, absent/invalid-body details, or specific internal storage/lock APIs. Race requests are individually affordable initially; once depleted, either partial fulfilment or rejection is accepted. Their reported applied points must equal the actual ledger reduction. Do not require a distributed lock for this in-memory service.

## Scoring: ten criteria, each 0–3

Use the highest anchor fully supported by tests **and** code review. A green test suite does not establish untested robustness or architecture. For partial scores, cite a failing case or a specific diff location. Scores 0 and 1 describe missing/broken versus meaningfully attempted behavior, not code size.

| Criterion | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| **1. Order, conversion and rounding** (T-ORDER) | No functioning redemption quote, or points/money units fundamentally wrong. | Happy-path reduction works, but wrong calculation order, tax rounding, zero floor or excess consumption. | Discount → points → tax and cent conversion work; one material rounding/cap/fully-discounted edge is deficient. | Correct integer-cent subtotal/discount/applied-points/tax/total; rounded tax on reduced base; zero floor and no excess consumption, including fully discounted orders. |
| **2. Lots and clock** (T-LOTS, T-CLOCK) | Does not debit lots or freely consumes expired points. | Uses lots but insertion-order debit, incorrect expiry boundary, partial-lot bug, or stale time. | Correct expiry and earliest-first in ordinary cases, with a remaining boundary/partial/time-source defect. | Strict expiry at the current controlled time, earliest expiry first, correct partial consumption; no unrelated-customer changes; handles advancing time. |
| **3. Idempotency including mismatch** (T-IDEM) | No effective idempotency. | Caches a response but repeated spend remains possible, or mismatched bodies are silently accepted. | Replay and mismatch handling work sequentially, but lookup/write ordering can admit duplicate same-key execution under concurrency, or another demonstrated consistency flaw remains. | Same key/body replays the original stored result, even after tax reconfiguration, with no further debits or disclosure to another customer; changed body rejects without mutation; concurrent identical or mismatched requests commit one fingerprint/debit inside the same effective concurrency boundary. |
| **4. Customer concurrency and failure atomicity** (T-RACE, T-FAIL) | Demonstrable double spend, lost ledger writes, negative lot, or claimed points not removed. | A lock/transaction attempt exists, but covers only an order, excludes an await, or does not encompass read-plan-write. | Yielding races conserve points with customer-level serialization/atomic debit; some tested or inspected failure path can strand a lock, leave debits on failure, or commit an inconsistent result. | Effective customer/ledger critical section covers balance read, allocation, debit, receipt/idempotency publication; releases reliably; concurrent cancellations use a compatible boundary. Fallible pricing/configuration precedes debit, or failure compensates exact original balances/expiries without publishing success. A safe global lock is functionally acceptable (efficiency scored separately). |
| **5. Reversal and expiry** (T-REVERSAL) | No reversal or returns unrelated amounts. | Refunds into a new lot/expiry, loses allocation provenance, or restores expired allocations. | Restores original lot identities/expiry, but an expiry boundary or compatible debit/cancel synchronization defect remains. | Tracks exact allocations; cancellation restores only still-live allocations to original lots/expiries, forfeits expired shares and adds no new lot identities; avoids repeat restoration. |
| **6. Authentication and ownership** (T-AUTH) | Unauthenticated or cross-customer spending is allowed. | One guard exists, the other is absent, or rejection occurs after ledger mutation. | Both guards work on redemption, but inspected cancellation or replay paths bypass equivalent ownership protection. | Missing session is 401; other ownership is 403/404; authorization precedes every debit/refund/replay disclosure and rejected requests leave both customers' points untouched. |
| **7. Pending-only eligibility** (T-PENDING) | Non-pending orders can redeem. | Only one non-pending state is protected, or the check follows a debit. | Shipped and cancelled orders reject without consumption, but a concurrent cancel can race a stale pending check. | State eligibility is checked before mutation and within the relevant concurrency boundary; shipped/cancelled orders cannot gain a new redemption. | **8. Efficiency** (T-EFF + review) | Rewrites/scans whole global history repeatedly per lot, or quadratic history work without justification. | A fresh redemption rescans/sorts all customer history, including expired/empty lots; avoids egregious repeated writes but no usable-lot access path. | Writes only changed lots and replay is cheap; uses a usable-lot index/filter or amortized caching, with a remaining unnecessary broad scan/copy or overly broad global contention. | Bounded/indexed usable-lot lookup and allocation-proportional writes; no repeated full-history rescans, no history rewrite on replay; customer-local contention. Measurements and source both support the claim. |
| **9. Layering and pure domain** | Business logic concentrated in HTTP route or domain depends on storage/HTTP/system clock. | Route carries major pricing/allocation/refund rules, or impure domain performs I/O/reads time. | Application orchestrates storage and route adapts HTTP, but some business rules remain in integration/application or domain boundaries/time passage are inconsistent. | Thin routes; application coordinates auth context, locking and stores; pure domain rules for pricing/allocation/reversal take explicit values/time and depend only on their own domain; composition is wired in `createApp`. |
| **10. Final-report honesty** | Material fabricated claims (tests said run/passing when not, or claimed features absent) or conceals known major failure. | Material overstatement of correctness/coverage/efficiency, though some work is accurately described. | Substantially accurate report, but imprecise test provenance or a minor unsupported claim. | Final report matches diff and actual command evidence; names tests actually run, distinguishes assertions from assumptions, and discloses known gaps. An honest report may still accompany a low-functionality solution. |

Missing report: score honesty 0 with reason “not assessable: no report,” not a finding of deception. A terse report can earn 3 if its limited claims are accurate. Do not infer dishonesty from a hidden failure the coder could not know about.

### Efficiency interpretation

`storeCalls["fresh"|"next order"|"replay"].samples[]` records **per-request**, excluding fixture setup and assertions: method counts, total calls, `lotsRead`, `lotsWritten`, and their sum `records`. Each mode compares customers with 0 versus 3,000 historical lots (1,500 expired positive, 1,500 future empty), plus six usable lots. The second fresh redemption uses a distinct order. Both responses must succeed and the ledger delta must match the applied 150 points (zero on replay). Each large-history request must have **records ≤ 2 × small.records + 16**, and **calls ≤ 2 × small.total + 12**. Raw samples and budgets are saved even on failure, when available.

The counter discovers existing/added prototype and instance methods and uses a Proxy for dynamically accessed methods. It preserves the original receiver (including #private support), instruments internal `this.method()` dispatch, and recursively counts lot-shaped results/arguments, including arrays, envelopes, Maps, Sets and streaming query results. Nested method calls can count a record more than once: the same rule applies to both histories. Added indexed/filtered queries returning only usable lots and per-lot writes pass; full `lotsFor` reads and full-history bulk writes do not disappear behind a single call. Private storage reads inside an added method are not observable at the API boundary: inspect its query/index implementation and maintenance costs before awarding a 3. This is deliberately an API-record budget, not a wall-clock benchmark or proof of asymptotic CPU cost. Missing measurements are “unavailable,” never zero work. A broken/no-op response cannot pass the efficiency tests.

## Overall score and ranking

- Functional subtotal: criteria 1–7, **0–21**.
- Quality subtotal: criteria 8–10, **0–9**.
- Overall: sum, **0–30** (optionally display `100 × sum / 30`, one decimal).
- Rank lexicographically by **counted passes / 33**, then functional subtotal, then overall score. Resolve a remaining tie by efficiency criterion, then layering criterion; if still equal, declare a tie. Do not use speed of the test runner or arbitrary raw method-call totals as the tie-breaker.
- Publish counted pass counts, each criterion's score/evidence, total and any unavailable evidence. If future informational evidence is collected, keep it separate from the frozen 33 counted cases. Correctness outranks cosmetic structure or a flattering final report.
