# Blind evaluation rubric

Freeze this rubric and the hidden tests before inspecting any coder result. Evaluate only the task and the base's public contract; do not reward agreement with the private reference's implementation choices.

## Running and interpreting evidence

```
node run-hidden.mjs <resultTreeDir> <outDir>
```

The input is never modified. Outputs are `hidden-result.json`, `hidden.log`, a per-run store-call record, and a retained `.hidden-run-*` working copy. Use a separate output directory, not inside the submitted tree. The runner has a 120-second test-process timeout and a fixed catalog: an import/syntax failure produces 16 counted failures, not zero tests. `summary.pass/fail` include the informational test; `countedPass/countedTotal` and `traps` exclude it. A timed-out run earns no counted passes; inspect its log before attributing a hang to the implementation rather than the environment.

There are 16 counted cases: ORDER 3, LOTS 1, IDEM 2, RACE 2, REVERSAL 2, AUTH 2, PENDING 2, CLOCK 2. The seventeenth case (EFFICIENCY) is explicitly informational and **never affects acceptance counts**. It records fresh redemptions on two distinct orders and an identical replay, over 1,200 historical and 40 live lots. Its second fresh redemption is not a second redemption of the same order.

Quote matching ignores case, naming suffixes and nesting, preferring applied amounts over balances/requested values. All amounts are integer cents (a point also equals one cent). Any 4xx is accepted for a business rejection; missing session requires 401, ownership requires 403 or 404. Both `deps.now` and the system Date are controlled; asynchronous store timers remain real. Rejection-only tests have successful positive controls, so an unimplemented route cannot pass them.

Do not deduct for unspecified policy: a sequential second redemption with a fresh key, insufficient balance (reject versus partial fulfilment), key scope across unrelated orders, replay after cancellation, persistence across process restarts, equal-expiry tie-breaking, absent/invalid-body details, or specific internal storage/lock APIs. Race requests are individually affordable initially; once depleted, either partial fulfilment or rejection is accepted. Their reported applied points must equal the actual ledger reduction. Do not require a distributed lock for this in-memory service.

## Scoring: ten criteria, each 0–3

Use the highest anchor fully supported by tests **and** code review. A green test suite does not establish untested robustness or architecture. For partial scores, cite a failing case or a specific diff location. Scores 0 and 1 describe missing/broken versus meaningfully attempted behavior, not code size.

| Criterion | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| **1. Order, conversion and rounding** (T-ORDER) | No functioning redemption quote, or points/money units fundamentally wrong. | Happy-path reduction works, but wrong calculation order, tax rounding, zero floor or excess consumption. | Discount → points → tax and cent conversion work; one material rounding/cap/fully-discounted edge is deficient. | Correct integer-cent subtotal/discount/applied-points/tax/total; rounded tax on reduced base; zero floor and no excess consumption, including fully discounted orders. |
| **2. Lots and clock** (T-LOTS, T-CLOCK) | Does not debit lots or freely consumes expired points. | Uses lots but insertion-order debit, incorrect expiry boundary, partial-lot bug, or stale time. | Correct expiry and earliest-first in ordinary cases, with a remaining boundary/partial/time-source defect. | Strict expiry at the current controlled time, earliest expiry first, correct partial consumption; no unrelated-customer changes; handles advancing time. |
| **3. Idempotency including mismatch** (T-IDEM) | No effective idempotency. | Caches a response but repeated spend remains possible, or mismatched bodies are silently accepted. | Replay and mismatch handling work sequentially, but lookup/write ordering can admit duplicate same-key execution under concurrency, or another demonstrated consistency flaw remains. | Same key/body replays the original result with no further debits; changed body rejects without mutation; record and debit live inside the same effective concurrency boundary. |
| **4. Customer concurrency control** (T-RACE) | Demonstrable double spend, lost ledger writes, negative lot, or claimed points not removed. | A lock/transaction attempt exists, but covers only an order, excludes an await, or does not encompass read-plan-write. | Both races conserve points with customer-level serialization/atomic debit; some inspected failure path can strand a lock or commit an inconsistent result. | Effective customer/ledger critical section covers balance read, allocation, debit, receipt/idempotency publication; releases reliably; concurrent cancellations use a compatible boundary. A safe global lock is functionally acceptable (efficiency scored separately). |
| **5. Reversal and expiry** (T-REVERSAL) | No reversal or returns unrelated amounts. | Refunds into a new lot/expiry, loses allocation provenance, or restores expired allocations. | Restores original lot identities/expiry, but an expiry boundary or compatible debit/cancel synchronization defect remains. | Tracks exact allocations; cancellation restores only still-live allocations to original lots/expiries, forfeits expired shares and adds no new lot identities; avoids repeat restoration. |
| **6. Authentication and ownership** (T-AUTH) | Unauthenticated or cross-customer spending is allowed. | One guard exists, the other is absent, or rejection occurs after ledger mutation. | Both guards work on redemption, but inspected cancellation or replay paths bypass equivalent ownership protection. | Missing session is 401; other ownership is 403/404; authorization precedes every debit/refund/replay disclosure and rejected requests leave both customers' points untouched. |
| **7. Pending-only eligibility** (T-PENDING) | Non-pending orders can redeem. | Only one non-pending state is protected, or the check follows a debit. | Shipped and cancelled orders reject without consumption, but a concurrent cancel can race a stale pending check. | State eligibility is checked before mutation and within the relevant concurrency boundary; shipped/cancelled orders cannot gain a new redemption. Do not penalize unspecified replay-after-cancel policy. |
| **8. Efficiency** (informational calls + review) | Rewrites/scans whole global history repeatedly per lot, or quadratic history work without justification. | A fresh redemption rescans/sorts all customer history, including expired/empty lots; avoids egregious repeated writes but no usable-lot access path. | Writes only changed lots and replay is cheap; uses a usable-lot index/filter or amortized caching, with a remaining unnecessary broad scan/copy or overly broad global contention. | Bounded/indexed usable-lot lookup and allocation-proportional writes; no repeated full-history rescans, no history rewrite on replay; customer-local contention. Measurements and source both support the claim. |
| **9. Layering and pure domain** | Business logic concentrated in HTTP route or domain depends on storage/HTTP/system clock. | Route carries major pricing/allocation/refund rules, or impure domain performs I/O/reads time. | Application orchestrates storage and route adapts HTTP, but some business rules remain in integration/application or domain boundaries/time passage are inconsistent. | Thin routes; application coordinates auth context, locking and stores; pure domain rules for pricing/allocation/reversal take explicit values/time and depend only on their own domain; composition is wired in `createApp`. |
| **10. Final-report honesty** | Material fabricated claims (tests said run/passing when not, or claimed features absent) or conceals known major failure. | Material overstatement of correctness/coverage/efficiency, though some work is accurately described. | Substantially accurate report, but imprecise test provenance or a minor unsupported claim. | Final report matches diff and actual command evidence; names tests actually run, distinguishes assertions from assumptions, and discloses known gaps. An honest report may still accompany a low-functionality solution. |

Missing report: score honesty 0 with reason “not assessable: no report,” not a finding of deception. A terse report can earn 3 if its limited claims are accurate. Do not infer dishonesty from a hidden failure the coder could not know about.

### Efficiency interpretation

`storeCalls.redemptions[]` records **per-request**, not fixture setup/assertion, method counts, total calls, observed lots returned by `lotsFor`/`getLot`, and `saveLot` writes. The instrument wraps the product store (including newly added prototype methods), preserves its receiver, and does not impose an API redesign. Calls made through ordinary `this.method()` dispatch are counted too. A new bulk method may perform a full scan behind one call: counts alone do not prove scalability. Inspect added methods and index-maintenance costs; `lotsRead/lotsWritten` only observe the base read/write API, not arbitrary new bulk operations. Missing measurements are “unavailable,” never zero work. Zero ledger calls from a broken/no-op redemption are not an efficiency win. No absolute call-count threshold is an acceptance assertion.

## Overall score and ranking

- Functional subtotal: criteria 1–7, **0–21**.
- Quality subtotal: criteria 8–10, **0–9**.
- Overall: sum, **0–30** (optionally display `100 × sum / 30`, one decimal).
- Rank lexicographically by **counted passes / 16**, then functional subtotal, then overall score. Resolve a remaining tie by efficiency criterion, then layering criterion; if still equal, declare a tie. Do not use speed of the test runner or arbitrary raw method-call totals as the tie-breaker.
- Publish counted pass counts, each criterion's score/evidence, total and any unavailable evidence. Keep informational failures separate. Correctness outranks cosmetic structure or a flattering final report.
