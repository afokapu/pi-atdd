Title: Declare the URN side segment as frontend or backend by real ownership
Given: A file in a Bun-realization repo carries a six-segment URN header; in a stack-spanning repo side cannot be inferred from language or runtime.
When: The header exists or is written/edited, or the file's implementation changes which side owns it.
Then: Segment 4 (`{side}`) must be exactly `frontend` for browser-owned or `backend` for server-owned implementation.
Prefer:
- During GREEN repair, derive side from where responsibility lives, not merely from file syntax.
- Treat server-rendered htmx fragments as backend and browser-resident behavior as frontend.
- When the rest of the URN is correct, change only the side segment.
Avoid:
- Moving implementation between client and server just to fix a header.
- Using `Runtime:` as a substitute for the side decision.
- Any value outside `frontend`/`backend`.
Unless:
- URNs that are not six segments are skipped.
- `Runtime:` is a different axis — a `backend` file may declare `Runtime: isomorphic`.
Why: In a full-stack Bun repo one language and runtime span both halves, so segment 4 alone says which side a module belongs to and must be declared per file (unlike Vite repos, frontend by construction, or python-pytest services, backend by construction, where it is near-redundant).
