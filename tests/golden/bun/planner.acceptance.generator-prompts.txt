Title: Give each acceptance field its own generator prompt sourcing that field's rule
Given: You are composing or maintaining the generator prompts that author acceptance fields
When: you write or change the prompt for any of id, urn, harness, route, given, when, then
Then: Give each field its own prompt, and have that prompt source its field's section of the acceptance convention and state that section's rule as a requirement.
Prefer:
- id prompt requires AC-{STEP}-{NNN}: step code + zero-padded index.
- urn prompt requires derivation via URNBuilder.acceptance from wagon slug, WMBT ID, harness code, sequence.
- harness prompt requires the harness that best exercises the outcome (unit/http/event/ws/e2e/...).
- route prompt requires route.layers and route.sequence, flowing presentation -> application -> domain -> integration.
- given prompt requires only needed preconditions (auth, builders, time, stubbing, knobs) before the action runs.
- when prompt requires the trigger in the harness-specific shape (http request, unit target, event topic, etc.).
- then prompt requires assertions proving the outcome (status, body, headers, error, metrics, etc.).
Avoid:
- One generic prompt that writes all fields at once.
- A field prompt that does not source its section, or that softens its rule (e.g. hand-built URNs, harness picked by habit, unneeded preconditions, generic triggers, assertions not tied to the outcome).
Why: Each acceptance field has its own authoring rule in the acceptance convention, so each field's prompt sources that section.
