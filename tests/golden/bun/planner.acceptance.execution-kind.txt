Title: Declare execution_kind on every acceptance, separate from harness/category
Given: You author or edit an acceptance, selecting harness code/type and category as usual.
When: You classify the runtime environment it runs against.
Then: Add execution_kind as a separate axis: hermetic_integration (real subject, boundary shape and integration sequence, no live external infrastructure) or live_smoke (verified against real live HTTP, DB, auth or deployment).
Prefer:
- Select harness/category exactly as before, then add execution_kind.
- hermetic_integration when the real integration runs without live infrastructure.
- live_smoke when confidence comes from live infrastructure; SMOKE stays the live-infrastructure tier.
Avoid:
- Encoding runtime environment in harness codes/types or category, or changing those enums.
- Marking hermetic_integration an acceptance that calls live infrastructure.
- Fakes (cassettes, recorded LLM responses) in hermetic_integration without a declared fidelity contract.
- Treating hermetic_integration as a substitute for SMOKE's live confidence.
Why: Live vs hermetic is a different question from harness or category; a separate axis keeps those enums stable while making live-infrastructure dependence explicit.
