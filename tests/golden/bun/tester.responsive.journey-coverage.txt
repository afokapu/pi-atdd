Title: Give every exposed frontend journey a RESP browser spec
Given: A journey whose entrypoint is exposed and whose `surfaces` include `frontend` (or declare none) exists in the plan
When: the journey set is declared, changed or evaluated (including plan-only changes and already-declared journeys)
Then: That journey MUST have a journey spec (browser spec) bound to it by `// Journey: <journey id>` carrying a RESP test URN.
Prefer:
- Add `e2e/<journey>.responsive.e2e.ts` bound with `// Journey: <journey id>`.
- Add the RESP spec as soon as the plan declares a new exposed frontend journey.
Avoid:
- Counting a unit test that merely mentions a journey URN in a string as RESP coverage.
- Assuming a misnamed spec escapes judgement: any test file with a journey marker in its header comments is judged as a browser spec.
- Writing RESP specs for internal journeys or journeys whose surfaces exclude frontend just to raise coverage.
Unless:
- The journey is internal, or its exposed entrypoint `surfaces` exclude `frontend` — there is no screen to fit, so it is out of scope.
- Vendored and generated trees (`node_modules`, `dist`, `build`, `_generated`) are never scanned.
Why: Every screen a user can reach should be proven to fit from mobile to desktop; exposed journeys are exactly those screens, and new ones appear here as soon as the plan declares them.
