Title: Security tests assert on denial
Given: A Bun test whose URN header kind segment is SEC, RLS or AUTH (the header, not the filename, is authoritative).
When: Writing, changing or reviewing that security test.
Then: Prove the refusal named by the security acceptance: for the unauthorized or under-privileged stimulus it describes, assert the denial signal (e.g. 401, 403, permission error, rejection, throw) produced by the bound protected operation.
Prefer:
- Construct the missing, invalid or insufficient authorization state the acceptance describes; exercise the real protected boundary.
- Required witness when the acceptance protects a mutation or other side effect: also assert the protected state/action remains unchanged — returning 403 after performing the mutation is still a security failure.
- A happy-path case is optional and welcome, but cannot replace the denial case.
- `const res = await fetch("/orders", { method: "POST" });   // anonymous` then `expect(res.status).toBe(403);` (status only; for a protected mutation add the unchanged-state check above).
Avoid:
- A happy-path permission case as the only security proof.
- An unrelated or generic 403 not produced by the bound protected operation, added to satisfy the detector.
- Mocking away the authorization decision the acceptance must prove.
- For a protected mutation/side effect, asserting only the denial status without checking the effect did not occur.
Why: A happy-path-only security test is a silent green gap: it passes CI and counts as covering the security acceptance while proving nothing about the denial path, the only path the acceptance is about.
