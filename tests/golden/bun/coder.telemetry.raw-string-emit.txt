Title: No undeclared raw-string telemetry names
Given: A non-test source file in a repository that has adopted a telemetry tracking plan
When: An emit-like call (emit, emitted, track, capture, record, logEvent, emitEvent, sendEvent; function or method) passes an event-shaped string literal as first argument
Then: That string MUST be a concrete telemetry id declared in the tracking plan.
Prefer:
- Declare the item first (e.g. telemetry/commons/response-invocation-accepted/event.be.json), then emit through the plan: telemetry.emit("telemetry:event:be:commons:response-invocation-accepted", { ... });
- Once generated contracts ship, emit via the contract constant, not a raw string.
Avoid:
- Emitting an undeclared event name as a raw string literal.
- Hiding an undeclared name behind a variable or template literal to dodge the check.
- Treating this name-resolution check as proof of transaction ordering or other runtime properties.
Unless:
- Test files: assertion code legitimately names events it is proving.
- Non-event-shaped strings (log levels like "info", single-word keys) — some other concern.
- Repository has not adopted the tracking plan (inert until adoption).
Why: Undeclared event strings are how tracking plans rot: the string compiles, the dashboard never fills, and nobody owns the difference. The registry is the list of names that may be emitted.
