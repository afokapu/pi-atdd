Title: Serve HTTP with Bun.serve, not a node-compat framework
Given: non-test source of a full-stack Bun application
When: the HTTP server, a route, handler or middleware is added or modified
Then: Serve HTTP with Bun.serve; construct no Express, Fastify, Koa or node:http/node:https createServer server.
Prefer:
- Express middleware behavior as ordinary function composition around Bun.serve handlers
- During GREEN: add only the route, handler or middleware composition the current acceptance requires; reuse the existing Bun.serve instance and routing pattern; when replacing a forbidden framework in new work, migrate only the path required for correct behavior
- Assemble and post-process htmx fragments with HTMLRewriter in the Bun server
Avoid:
- Introducing Express, Fastify, Koa or node:http for convenience
- A compatibility abstraction over a forbidden server
- Rewriting unrelated routes
- Serving even one route via a foreign framework: its middleware ecosystem follows and the migration silently stops halfway
Unless:
- Test files: a throwaway test server is not an application server
- Non-HTTP createServer( (test double, unrelated factory): known name-match imprecision; rename it (no per-rule scope)
Why: Not taste; load-bearing for the stack decision: only Bun.serve has native routing, WebSocket upgrade, streaming and HTMLRewriter (a streaming HTML transformer available only through the Bun server, used for htmx fragments). Running e.g. Express under Bun keeps the npm middleware surface, forfeits native primitives and breaks the deployment story ('bun run server.ts', no bundle, no node_modules at runtime) — silently, because the compat layer works.
