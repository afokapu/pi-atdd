Title: Reference color tokens instead of raw color literals in UI files
Given: A repository that has a design root, and a UI file anywhere in it (.tsx, .jsx, .html, .htm, .css, or HTML authored in .ts/.mts literals) outside the tokens/foundations layer
When: A color is written in a CSS declaration, style attribute, <style> block, JSX style={{…}} object, or fill/stroke/bgcolor attribute
Then: Define the required color once in the tokens layer and reference that token (`var(--…)`) from UI code; never write a raw hex, rgb()/rgba() or hsl()/hsla() literal in the value.
Prefer:
- During GREEN: reuse an existing semantic color token when it already expresses the required role.
- During GREEN: add the smallest new semantic token only when the current visual behavior needs a distinct value.
- During GREEN: change only the affected UI reference.
Avoid:
- Do not broaden: retheming unrelated components.
- Do not broaden: duplicating an existing token under a new name.
- Do not broaden: using a raw literal as a temporary shortcut.
Unless:
- Custom property definitions (`--danger: #b91c1c`) define tokens wherever they live and are not flagged.
- Named colors (`red`, `white`) and `currentColor`/`transparent` are not flagged.
Why: A raw color is a theme decision made in one place: it does not follow dark mode, drifts from the palette, and nobody can find it when the palette changes.
