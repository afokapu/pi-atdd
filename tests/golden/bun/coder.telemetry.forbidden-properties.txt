Title: Keep plan-forbidden properties out of emit calls
Given: After adoption, an emit-like call (a telemetry emit whose first argument is a declared concrete tracking-plan item id) with a properties object literal following that argument on the same statement.
When: The call exists or changes, or the named item's forbidden_properties list or the call's item id changes.
Then: No top-level named key of the properties object MAY match a property the plan forbids on that item, compared after stripping separators and folding case (shorthand properties carry no name and are not scanned; nested objects are judged at their own level).
Prefer:
- Pass the identifier, not the thing it identifies, and leave out any property the named item's plan forbids.
Avoid:
- Attaching raw payloads, secrets or prompts the plan forbids on the named item.
- Evading the check by renaming case/separators (snake_case vs camelCase) instead of removing the property.
- Treating properties the plan merely does not declare as forbidden or removing them for this rule; undeclared-key drift is the generated contract's concern.
Unless:
- The call names an id the registry does not hold: that is the raw-string rule's finding; double-reporting here would be noise.
- Inert until adoption, like every rule in this family.
Why: The forbidden list is a privacy and cost promise, so it is enforced where data leaves: the emit call itself, against the plan entry the call names.
