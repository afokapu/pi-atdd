Title: Input-validation tests assert on rejection
Given: A Bun test whose URN carries an INPUT, VALIDATION or VALIDATE kind segment
When: the test is scanned
Then: It MUST drive the malformed/missing/adversarial input named by the acceptance through the production boundary and assert its rejection (.rejects, toThrow, 400, 422, invalid, reject, or an error expectation) for that specific invalid condition.
Prefer:
- Construct the malformed, missing, boundary or adversarial value the acceptance names.
- Send it through the same boundary production receives.
- Assert the acceptance-specific rejection: exact error, 400/422 response, rejection or throw.
- When accepting the bad input could create or mutate state, also assert the rejected request left that protected side effect absent.
Avoid:
- Testing only a well-formed payload (it proves only that the parser works on good input; a well-formed payload proves nothing about adversarial input).
- Triggering some unrelated error and treating any rejection as proof (the detector may not flag this, but it does not witness the declared invalid condition).
- Bypassing the production validation boundary with a direct fixture assertion.
Why: An input-validation acceptance is about BAD input, which a happy-path test never touches — the same silent-green-gap shape as security-auth. It is grouped with the security family because unvalidated input is the entry point for most of what the security rules defend against.
