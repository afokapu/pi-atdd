Title: Coordinate durable work only through atdd-flow records
Given: The workflow profile is active (durable YAML records live in the separate workflow root) and you act as any seat — main, coordinator, driver or operator — including while implementing an assigned task, launching a seat or creating initial records.
When: You take any workflow step: start or resume, implement and prove a task, change task or seat state, message, hand over, transfer, review, launch or retire a seat.
Then: Change task, seat, checkpoint, handover and thread records only through the installed atdd-flow CLI, acting from what those records currently say (read them before acting).
Prefer:
- Before workflow action run `atdd-flow --help` to discover the installed commands and current syntax (if the executable is project-local and not on PATH, `bunx atdd-flow --help`); treat that help output as the command authority.
- Read the task, seat, checkpoint and thread YAML before acting; start or resume from the current seat, checkpoint, assigned tasks and relevant threads. A replacement agent resumes from those records and never depends on a conversation with its predecessor.
- Driver: start only your assigned ready task; treat its done_when criteria as the delivery scope and implement the smallest effective change (see policy.phase-loop). Work criterion by criterion, continuing from the next unmet done_when criterion through implementation, verification and proof: complete the required implementation, run the relevant tests and ATDD Bun checks, correct failures caused by your work, record proof for every done_when criterion, move the task to review and send your coordinator a result. Continue until the task is review-ready (implementation and verification complete, proof on every criterion, task in review, coordinator has the result) or explicitly blocked.
- If completion is impossible, block explicitly: record the blocker, checkpoint the exact current state and next action, and notify the coordinator.
- At a responsibility boundary (shared vocabulary, endpoint shape, contracts, artifact ownership or another participant's responsibility), send the concrete boundary question to your coordinator. The coordinator aligns directly with affected coordinators through the existing durable thread mechanism, resolves only the minimum shared vocabulary, interface, ownership or responsibility split needed for the current work, prefers an existing convention or contract over inventing one, records the agreement in the relevant thread and communicates the result back to affected drivers.
- Route messages: drivers send normal work messages to their coordinator (never directly to the operator or main seat); coordinators may escalate a concrete decision or incident directly to the operator; main seats are the normal repository-main integration gateway to the operator; a receipt or result addresses the seat that made the request, not every historical participant in the thread.
- Drivers hand work back to their named coordinator for integration and validation; the named coordinator hands a reviewed integration candidate to main; only main completes normal integration-to-main gates and publication.
- Topology for new projects: `main@project` is the sole primary-checkout and `main`-branch coordinator; a named `coordinator.stream@project` works only from its own linked `integration/stream` branch and worktree and integrates bounded driver delivery rather than acting as a hidden feature driver; a driver it coordinates derives its governed base from that exact integration head, while a main-coordinated driver derives from main. Reject nested coordinator lineage, mismatched base/worktree placement and ambiguous placement rather than guessing.
- Transfer active task accountability only with `atdd-flow task transfer`. The current coordinator may transfer; main may only with one applicable immutable `operator@desk` `task-transfer-authorization/v1` message whose project, task, from, to, reason and exact target branch/head match the requested transfer before mutation (only `operator@desk` may create that typed authorization). Accept only main or a valid named integration coordinator as target and atomically derive the new governed base from the accepted target head. Provenance (from/to/reason/exact-head/effective-time) is append-only and prior task, phase, review and message evidence stays attributable. Reject same-target, duplicate, nested, mismatched, unauthorized or manually rewritten transfers. A transfer never moves or changes any seat, branch, runtime binding, worktree, dirty state or evidence artifact.
- Context handover, every seat (main, coordinator, driver, operator): begin at 80% and no later than 90% context usage, depending on context (not a single fixed threshold). The primary path, which every seat self-services, is same-session compaction: validate and record the handover/checkpoint, pass the recovery bundle as the compaction summary, and continue in the same Pi session, JSONL, Herdr pane and Flow binding. If compaction is unavailable, fails an invariant, or the session is stuck, Flow uses the verified PR #111 new-pane successor path as the fail-closed fallback; operator intervention is fallback-only. Caveat: the runtime prompt and behavior remain pending compaction T2/T3; until they land this states the target policy and the runtime prompt is unchanged.
- To hand over: finish or cleanly undo the current atomic step (commit, post, receipt) and start nothing new; write the handover using the template, validate it with `atdd-flow handover <address> --check --file <path>`, fix every reported problem, and record it with `atdd-flow handover <address> --file <path>`. The seat's handover.yaml is the one durable handover record; it sits beside the checkpoint and never replaces it. On the fallback path the old session then makes no further tool calls and a fresh session bound to the same seat continues; after compaction the same session continues.
- Handover content: point to toolkit conventions, never restate or override them; list open items only, use exact IDs and mark state [verified|assumed]; 150 lines is a ceiling, not a target. Recording rejects a missing or malformed header or Runtime line, a missing, duplicate or out-of-order section, more than 150 lines, a wrong supersedes value, and vague references without an exact identifier (details in verifier_detail[0]).
- Handover template:
HANDOVER <seat-address> | <UTC ts> | handover-id <id> | supersedes <id|none>
Runtime: <application> <session>:<pane> | <agent> session <id> | model <provider/model> | context <NN>%
1. SEAT, AUTHORITY, TOOLKIT AND HAZARDS
- Seat: <address> (<role>), project <project>; reports to <addr>; directs <addrs|none>
- Worktree: <path> @ <branch> <sha> (<clean | dirty: files>)
- Toolkit in force (this worktree): Flow <ver> / Bun <ver> | declared=locked=installed: <yes | NOT CURRENT: detail> | runtime binding: <Flow ver | unverified>
- Governing conventions for current phase: <convention ids> (pointers only)
- Profile/ratchet state: <profile> <reject-new|strict> | activated ratchets (never modify): <list|none>
- Authorizations in force: <scope> | granted by <addr> | ref <msg-id> | expires <ts|never>
- Seat-specific constraints (beyond the instruction file): <list|none>
- Hazards / known bugs / workarounds: <list|none>
- Dead ends (tried, failed, do not repeat): <what> | ref <id> (or none)
2. OPEN WORK AND IN-FLIGHT OPERATIONS
- <project>/<task-id> | <status/phase> | assignee <addr> | [verified|assumed]
  ref: <PR#/sha/pane>; last evidence <msg-id>; state: <one line>
- IN-FLIGHT: <operation> | started <ts> | check: <exact command> | retry-safe: <yes|no|why>
- Session-only knowledge: <facts learned, not recorded in Desk> (or none)
3. DEPENDENCIES (both directions)
- WAITING ON: <what> | <addr> | since <ts> | ref <msg-id> | follow up at <ts>
- OWED BY ME: <what> | to <addr> | due <ts> | ref <msg-id>
- DECISION PENDING: <question> | owner <addr> | options A/B + recommendation | ref <id>
- RECEIVED, NOT YET ACTED ON: <msg-id> | from <addr> | needed action
(or: none, per subsection)
4. RESUME PROCEDURE AND NEXT ACTIONS
Verify first:
- atdd-flow status seat <address>
- atdd-flow task open <project> <task-id>   (each open task)
- git -C <worktree> status && git log -1
- installed toolkit versions in <worktree> match section 1 (mismatch = discrepancy; report, do not self-upgrade)
- <each IN-FLIGHT check command>
Then, in order:
1. Read inbox; receipt pending messages lacking my receipt.
2. <concrete action with exact IDs>
- Resuming session: read the instruction file, then `atdd-flow handover show <address>`, run the handover's verification, reconcile it with the live Desk (the Desk wins), reconcile your inbox, report `RESUMED; verified N/M; discrepancies: ...` through your normal reporting route, and continue. Read a convention when its phase is acted on, not all on resume.
- Use `atdd-flow scout` only when repository scope is genuinely unclear or candidate files are numerous; use `atdd-flow focus-check` only before a likely scope expansion (new dependency, generalized abstraction, persistent schema, architecture change, adjacent refactor, unrelated defect). These are read-only Jev judgments that advise scope; they do not own correctness or completion.
- Launching a seat: new seats do not pin a model. The Desk's models.yaml lists launchable candidates ordered strongest to weakest; for ordinary launches ask Jev for the weakest available model sufficient for the seat's current active work; if Jev model selection is unavailable or low-confidence, use the strongest available configured model.
- Final review (Workflow/coordinator): between phases, let the next phase consume and semantically challenge the prior one while active ATDD Bun conventions enforce deterministically; reserve the explicit independent semantic reviewer (behavioral review: final semantic reconciliation after deterministic gates, before review -> done) for the final integration boundary. After the driver moves the task to review, run the deterministic ATDD Bun gates in the delivery worktree before launching the reviewer. Only after they pass may Jev answer bounded routing questions: classify the review surface as LOCAL, ASSEMBLED, JOURNEY or SYSTEM with routing signals (behavior-affecting vs behavior-preserving intent, highest relevant proof boundary, cross-path scope, consequence, reconciliation shape, runtime observability, confidence); treat low-confidence routing as SYSTEM. Map the routing result through models.yaml to a reviewer model, create a task-scoped reviewer responsibility in the delivery worktree, and supply inputs in this order: task criteria/source; relevant plan artifacts; deterministic gate evidence; executable proof; runtime/worktree; then implementation/diff context. Include the complete installed atdd-bun.review.behavioral-reconciliation convention in the reviewer prompt as the authoritative method — ATDD Bun owns the review method; Workflow owns routing, reviewer allocation, durable evidence and lifecycle enforcement.
- Reviewer: record durable structured evidence — intent sources, expected behavior, exercised boundary and evidence, observed behavior, reconciliation findings, a decision of APPROVE, RETURN or ESCALATE, rationale and confidence — and never mutate task state. Coordinator: APPROVE makes the current clean delivery commit eligible for completion; on RETURN move review back to in_progress; on ESCALATE leave the task in review or explicitly block it until authoritative intent is resolved. Only the coordinator moves review to done, and only when the latest behavioral-review attempt is complete, records APPROVE and matches the current clean delivery commit.
- Retiring a driver seat (the final housekeeping step for an idle driver seat, delegated to ATDD Bun): install the repository's local dependencies in a driver worktree before working in or retiring it. A coordinator uses `atdd-flow task done <project> <task> --by <coordinator> --retire-assignee` only when every task assigned to that driver in the project is done and the seat is intentionally being retired; it delegates to `atdd-bun worktree finish --delete-branch`, runs in the seat worktree but resolves ATDD Bun from the primary checkout's local node_modules/.bin, then the primary checkout's own source when it is the ATDD Bun package, then PATH — never the seat worktree's copy, which may pin an older toolkit that refuses its own retirement. A failed retirement leaves the task in review and writes a blocked checkpoint for investigation.
Avoid:
- Inventing flags, inferring command forms from memory, or relying on an older agent's instructions.
- Treating terminal pane history, a multiplexer, an optional judgment helper or an agent's private memory as durable coordination state; rewriting task YAML (e.g. to transfer accountability).
- Posting, approving or making a decision while claiming `operator@desk` (the human authority, not an autonomous agent identity) unless the human operator actually supplied it.
- A driver independently redefining a shared contract; using boundary coordination to redesign adjacent systems or solve hypothetical future needs; reopening a settled boundary decision without concrete implementation evidence that it cannot satisfy the task.
- Intentionally ending an autonomous work turn on an assigned in_progress task while required work remains actionable; treating successful code generation as task completion; silently leaving actionable required work unfinished.
- Removing a worktree, deleting a delivery branch or forcing cleanup through raw Git; using `--retire-assignee` while that driver still has undone tasks in the project.
- Adding a writer/reviewer pair after every development phase; invoking the semantic reviewer while a strict gate is red (return the discrepancy to the appropriate implementation phase instead).
- Letting Jev approve a delivery, decide semantic correctness, mutate task state or redefine intent; duplicating the behavioral-review methodology in the Workflow convention.
- Introducing an automatic merge executor, branch graph, daemon or scheduler as part of this workflow.
- Self-upgrading the toolkit when installed versions on resume differ from the handover (report it as a discrepancy).
Unless:
- A broader change is permitted when a done_when criterion requires it, the current design cannot correctly satisfy the task without it, or it is necessary to resolve a verified blocker.
- A driver waiting on a boundary decision continues any independent required work that remains actionable; mark the task blocked only when the unresolved decision prevents further meaningful progress.
- A task may be completed normally without retiring its assignee when that driver still has work (a driver seat may own more than one task).
- A live host may notify an agent to inspect its seat, but it never owns the durable state.
- An optional Jev scouting, focus, final-review-routing or model-selection judgment may advise execution, but never owns task state, proof, correctness or completion authority.
- A legacy Desk without models.yaml may continue to use its pinned seat agent.
- Legacy seat, task and thread identities remain readable without rename or mutation.
Why: A seat owns its runtime binding, branch and worktree, a task its delivery state and proof, a thread its conversation; keeping these durable records as the single source of truth lets any replacement agent resume and keeps evidence attributable, which panes, memory and advisory judgments cannot.
