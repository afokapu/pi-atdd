Title: Declare acceptance boundary kinds only from the controlled vocabulary
Given: An acceptance declares the named integration surfaces (boundary_kind values) it exercises
When: You write, edit or review its boundary_kind entries
Then: Use only values from the controlled boundary_kind vocabulary: argv, subprocess, filesystem, git, http_wire, llm_wire, cmux_rpc, env_config, db_wire, event_wire.
Prefer:
- Pick the value whose definition matches the surface exercised: argv = command-line argument vector passed to a process; subprocess = a child process spawned and observed; filesystem = files and directories read or written; git = a local git repository's objects, refs and config; http_wire = HTTP request/response envelopes (cassette when hermetic); llm_wire = LLM prompt/response envelopes (recorded/deterministic when hermetic); cmux_rpc = cmux RPC request/response messages; env_config = environment variables and configuration inputs; db_wire = database query/response envelopes; event_wire = event-bus publish/consume envelopes.
Avoid:
- Inventing, abbreviating or synonym-ing boundary_kind values outside the vocabulary — unknown values are rejected by tester.acceptance-violation.hermetic-fake-must-declare-contract.
- Listing `golden` as a boundary_kind: `golden` is a harness_code, NOT a boundary_kind (Decision #7).
Why: boundary_kind is a controlled vocabulary of named integration surfaces an acceptance exercises; unknown values are rejected.
