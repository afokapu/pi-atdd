Title: Commons application modules do not import integration
Given: A module under `commons/application/` or `shared/application/` (orchestration over ports it defines)
When: it adds or keeps an import resolving into the commons `integration/` layer
Then: The module MUST NOT import from the commons `integration/` layer.
Prefer:
- Canonical path: keep commons application code dependent on an application-facing port.
- Canonical path: let integration implement that port and the composition root supply it.
- During GREEN: first reuse an existing port that already represents the required capability.
- During GREEN: add the smallest missing port only when current behavior genuinely needs an outer capability.
- During GREEN: pass only the data or collaborator required by the acceptance.
Avoid:
- Importing integration directly as a shortcut to GREEN.
- Introducing a generalized service layer for future callers.
- Reorganizing unrelated commons modules.
Unless:
- Test files and vendored/build directories are never scanned.
- Bare npm specifiers resolve outside the project graph; not layer-checked.
- A file with no layer segment is outside these rules, not in violation.
Why: Application orchestrates through ports it defines; reaching into integration inverts the dependency and welds orchestration to a transport, so changing the transport changes the orchestration.
