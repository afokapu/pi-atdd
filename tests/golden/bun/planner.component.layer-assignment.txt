Title: Assign each component's layer from its artifact type and responsibility
Given: A planned component has an artifact type (events, states, data or configs) and a responsibility.
When: The planner assigns, changes or reassesses its layer, or its responsibility changes.
Then: Assign a layer from the artifact type's typical layers, chosen by responsibility: events → integration|application; states → domain|application; data → domain|application|integration; configs → application|integration.
Prefer:
- Events (publishers sit at boundaries): publishing to external systems → integration; emitting internal events → application.
- States: tracking core business state → domain; coordinating state/lifecycle → application.
- Data (spans layers by responsibility): business logic → domain; coordinating the workflow → application; persisting to a store → integration.
- Configs: coordinating setup → application; loading settings (e.g. from an external config store) → integration.
- Treat the mapping as the default, defensible placement, not an absolute prohibition: the rule is advisory (severity 2) — findings are reported but do not block.
Avoid:
- Placing an external event publisher in the domain layer.
- Deciding the layer case by case or from the component name alone, ignoring its responsibility.
Why: A typical-layer mapping per artifact type gives a default, defensible placement for each component, so layer assignment is consistent rather than guessed case by case.
