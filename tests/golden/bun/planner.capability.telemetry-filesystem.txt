Title: Map each telemetry URN to its telemetry/ directory of signal files
Given: A plan, wagon or acceptance declares telemetry:{theme}:{segments} URNs, or work touches, validates or generates from signal files under telemetry/.
When: You author, edit, rename or validate a telemetry URN, its signal files, or the manifest built from them.
Then: Keep each URN's signals in telemetry/{theme}/{segments}/ as files named {signal-type}.{plane}[.{measure}].json, with a measure suffix on metric signals and none on event signals.
Prefer:
- Split the URN's ':' and '.' into path segments (telemetry:mechanic:decision.choice -> telemetry/mechanic/decision/choice/).
- Metrics like metric.db.count.json; events like event.be.json.
- Planes: ui, ux, be, nw, db, st, tm, sc, au, fn, if. Measures: count, duration, latency, size, rate, percentage.
Avoid:
- Metric files without a measure suffix.
- Event files with a measure suffix.
- Planes or measures outside the controlled lists.
- Hand-editing the manifest; it is generated from telemetry/{domain}/{resource}/*.json.
Why: A deterministic URN-to-path mapping lets tooling resolve URNs to signal files and generate the manifest from the filesystem; signal type (OpenTelemetry metric vs analytics event) decides whether a measure is needed.
