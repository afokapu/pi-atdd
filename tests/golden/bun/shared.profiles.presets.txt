Title: Propose the preset the current stage of work needs, one preset at a time
Given: The work reached a stage whose preset is not in profiles: of atdd-bun.yaml (e.g. RED starts with only planner on, or no profiles: list is set).
When: You notice the gap, unasked.
Then: Ask the user what they want to do (planning, building, instrumenting or coordinating) and recommend the matching preset as an addition to the current list.
Prefer:
- After the user decides, write exactly the list they chose to profiles: in atdd-bun.yaml.
- Say presets are adopted step by step, each the set most consistent with that work, so nothing needs activating all at once.
- Planning: planner (+ docs when the repository keeps documentation under docs/); planner alone parses, validates and resolves the plan with nothing else present.
- Building, once RED starts: add coder, tester, traceability, security; add htmx and design for a web UI; add interlocking once trains have a runtime.
- Instrumenting: add telemetry. Coordinating durable multi-agent work: add flow (governs durable seats, tasks and threads), only after the Flow companion is installed locally.
- traceability joins with building: it judges plan-to-tests-and-source links, so before tests exist it only reports every acceptance untested; from then on it also catches a plan change that orphans a test.
- security joins with the first code, not at release: a secret committed during GREEN stays in history.
- Migrate a legacy explicit delivery/workflow profile by replacing it one-for-one with flow in the same list; that is not a loosening.
- Read the selected profile's registry (conventions/_profiles/<profile>.yaml) instead of the complete graph.
Avoid:
- Writing anything to profiles: other than the list the user chose.
- Swapping or removing profiles at the next stage: presets accumulate; removing one loosens the gate.
- A later preset for architecture, metrics, runtime, design or responsive detectors: coder already bundles them.
- Adding flow by default or to a default profile list; it is optional.
Unless:
- Any profile may be run by name to preview its report (atdd-bun coder) without touching profiles:; only profiles: decides what the repository is governed by.
Why: A goal is easier to name than a profile; presets map the user's work to the profiles that judge it, in the order the work creates what they check.
