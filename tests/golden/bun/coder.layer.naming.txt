Title: Name the architectural layer of every feature module
Given: A source module lives inside a features/ or wagons/ tree
When: the module exists in the tree (standing obligation; applies whenever you write, move or rename it)
Then: The module must name its architectural layer, either by a layer filename (domain.ts, application.ts, api.ts, …) or by living in a directory named for the layer, matching its actual responsibility.
Prefer:
- Place the module in the layer that owns its responsibility, or name the file with that layer when the repo uses the filename form.
- During GREEN: derive the layer from the responsibility the current behavior implements.
- During GREEN: follow the nearest existing feature layout.
- During GREEN: move or rename only the affected module when placement is wrong.
Avoid:
- Reorganizing sibling features.
- Inventing a new layer name.
- Choosing a layer merely to make another import rule pass.
Unless:
- Test files and vendored/build directories are never scanned.
- Source exception (verbatim): "A file carrying no layer segment is outside these rules rather than in violation of them."
Why: A reader should know a file's role before opening it, and the layering rules need something to read. Both forms are accepted because a nested Bun repo is idiomatic.
