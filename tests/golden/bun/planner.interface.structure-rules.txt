Title: Derive contract layout (FLAT, FACETED, COLLECTION) from the artifact name
Given: An artifact named {domain}:{resource}[.{category}] (colon = hierarchy, dot = facet; optional category for nested resources) is declared, or its contract schemas/tests are placed, moved or corrected
When: the planner chooses or states its contract layout under contracts/
Then: Determine the layout in order: (1) dot facet → FACETED contracts/{domain}/{resource}/{category}.schema.json; (2) resource holding multiple schema files → COLLECTION contracts/{domain}/{resource}/*.schema.json; (3) otherwise → FLAT contracts/{domain}/{resource}.schema.json.
Prefer:
- FLAT (single schema, single resource): tests contracts/{domain}/tests/{resource}_schema_test.*. Source examples: 'match:dilemma.current -> contracts/dilemma/current.schema.json # singular noun -> flat (NOT dilemma/current/current.schema.json)'; 'mechanic:decision.choice -> contracts/decision/choice.schema.json # single resource -> flat'; 'fragment:pool -> contracts/fragment/pool.schema.json'.
- FACETED (category as dot facet): tests contracts/{domain}/{resource}/tests/{category}_schema_test.*. Source examples: 'ux:foundations.color -> contracts/commons/ux/foundations/color.schema.json # has dot facet -> nested; faceted, alternative to collection'; 'ux:primitives.icon'.
- COLLECTION (one artifact, several related schemas in one directory): tests contracts/{domain}/{resource}/tests/*_schema_test.*; optional catalog.schema.json master index; each schema's metadata: collection: true, resource (same for all), member (identifies the schema). Source examples: 'ux:foundations -> contracts/commons/ux/foundations/*.schema.json # plural noun -> collection'; 'ux:primitives -> contracts/commons/ux/primitives/*.schema.json'.
- Example comments cue noun number (plural → COLLECTION, singular → FLAT); the source gives no precedence over the order in then.
- Unresolved source conflict: the dotted FLAT examples contradict 'dot → FACETED' with no stated criterion. Follow the order by default; if you depart, state the mapping in the plan and flag the ambiguity.
- Source's generic physical pattern is contracts/{domain}/{resource}[/{category}].json, while the concrete layouts use .schema.json; this .json vs .schema.json discrepancy is unresolved—name the extension explicitly in the plan.
Avoid:
- Over-nesting a single resource: 'fragment:pool -> contracts/fragment/pool/pool.schema.json' instead of contracts/fragment/pool.schema.json.
- Contract paths not derivable from the logical name (layout chosen ad hoc).
Why: A deterministic name→layout mapping lets the path be derived from the logical name, keeps simple resources flat and supports faceted and multi-schema resources without ambiguity; domain-based organization gives clear ownership and REST API mapping.
