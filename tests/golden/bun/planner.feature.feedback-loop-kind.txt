Title: Use the optional feature kind: feedback-loop only for producer->consumer correction loops
Given: You are authoring or editing a feature that carries (or will carry) an explicit optional `kind:` field, which classifies the feature's system archetype — including edits to the behaviour of an already-marked feature where `kind:` itself stays unchanged.
When: You save the feature with an explicit `kind:` present.
Then: The explicit `kind:` must be `kind: feedback-loop`, and the feature's behaviour must be a producer->consumer correction loop: a producer detects a condition and emits, a consumer receives and reacts, and the detecting predicate then no longer fires.
Prefer:
- Write exactly `kind: feedback-loop` — the only valid explicit value of feature_kind.
- Leave `kind:` absent for any feature that is not a correction loop; absence means producer-only and no kind validator activates.
- When editing an already-marked feedback-loop feature, re-check that the edited behaviour still closes the loop (detect+emit, receive+react, predicate no longer fires).
Avoid:
- Marking a producer-only feature (no consumer reaction closing the loop) as `kind: feedback-loop`.
- Writing any explicit `kind:` value other than `feedback-loop` (including `producer-only`, which is the default when the field is absent rather than a listed valid value).
- Skipping the check because you edited behaviour but not the `kind:` line of an already-marked feature.
Why: Feature kind classifies the system archetype; validators activate only for explicitly-marked kinds, so the optional field lets marked loops be validated while existing (unmarked) features are unaffected.
