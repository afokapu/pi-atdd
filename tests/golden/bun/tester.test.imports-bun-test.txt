Title: Import the test harness from bun:test
Given: A test file (`*.test.*`, `*.spec.*`) in a Bun stack whose workspace provider declares `bun` as the runner
When: the test file is written or changed
Then: Import its harness from `bun:test`; never import `vitest`, `jest`, `@jest/globals`, `mocha` or `chai`.
Prefer:
- Import the harness from Bun: `import { describe, expect, it } from "bun:test";` — Jest-compatible assertions, so usually only the import line changes.
- Run tests with `bun test`.
Avoid:
- `import { describe, expect, it } from "vitest";` — not run by the declared runner.
- Expecting a test kept on a foreign runner during migration to be exempt: it stays reported until it moves; the finding is the migration's explicit, reviewable open item.
- Toolchain sprawl: a foreign runner and transform pipeline in a toolchain premised on Bun running TypeScript directly.
Unless:
- The file is not a test file (a different smell, not scanned).
Why: This rule is strict because the ATDD cost exceeds sprawl: acceptance tests are the evidence a phase gate consumes, reported in terms of its declared runner; a foreign-harness test is coverage the gate believes ran but never did — a green gate with an unexercised acceptance. A test the gate cannot run is worse than no test.
