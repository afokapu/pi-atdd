Title: Keep design-system files from importing app or wagon code
Given: A file under a design root (directory named `design`, `design_system` or `design-system`)
When: it imports a relative path
Then: The import MUST NOT resolve outside the file's design root; the design system stays independent of app and wagon code.
Prefer:
- Pass app-specific values into design components, or move genuinely shared, design-owned types/constants inward.
- During GREEN: use props or existing design-system contracts for the current value.
- During GREEN: add only the smallest input surface the acceptance requires.
- During GREEN: move a type or constant only when it is truly owned by the design system.
Avoid:
- Importing a wagon through a barrel or alias.
- Relocating app-specific concepts into design code just to make the import legal.
- Broadening the fix by generalizing unrelated design APIs.
Unless:
- Test files (`*.test.*`, `*.spec.*`) and vendored/build directories are never scanned.
- Bare package specifiers (`hono/jsx`) are outside the project graph; not judged.
- Aliased specifiers are judged only when they name a design directory.
- A repository with no design root is not judged: no system to connect to yet.
Why: Wagons and app code import FROM the design system, never the reverse, keeping it wagon-agnostic; a system reaching into a wagon becomes part of it, can't be reused by the next one, and breaks when the wagon changes.
