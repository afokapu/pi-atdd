Title: Estimate feature footprint from WMBT, interface and layer cues
Given: A planner is sizing a feature
When: The planner estimates the feature's architectural footprint
Then: Derive the footprint from the feature's WMBTs, interfaces and component layers by mapping each estimation cue (signal -> footprint element) to its footprint element, rather than guessing a size.
Prefer:
- WMBT display/animation signals -> count a screen/view
- WMBT apply/validate signals -> count an endpoint
- WMBT reconcile/persist signals -> count a table/migration
- WMBT notify/retry/queue signals -> count async work
- New events -> count them (event count)
- External consumes/produces -> count integration points
- Backend repository-layer components -> count a table/migration
- Frontend presentation-layer components -> count the number of screens
Avoid:
- Estimating footprint without tracing it to WMBTs, interfaces and component layers
Why: WMBT verbs, interfaces and component layers are concrete signals of which architectural elements (screens, endpoints, tables, async work, events, integrations) a feature will need, so footprint estimates grounded in them are repeatable and feed footprint scoring.
