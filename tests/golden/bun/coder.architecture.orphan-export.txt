Title: Design-system components have a consumer
Given: A file whose first directory beneath a design root (a directory named `design`, `design_system`, or `design-system`) is `primitives`, `components`, or `templates` exports a capitalized component.
When: Such an export exists, or the coder adds, changes, or stops consuming one.
Then: Each such export MUST have a consumer: another non-barrel file (higher design layer or app code) whose import clause names it or default-imports it under that name; otherwise remove the export.
Prefer:
- Export a component only when a real consumer uses it.
- During GREEN: if the current acceptance needs it, wire that actual consumer to it.
- During GREEN: if added speculatively with no required consumer, delete it.
- During GREEN: keep only the smallest export surface the current behavior needs.
Avoid:
- Dummy consumers or synthetic imports.
- Keeping speculative components "for later".
- Exposing unrelated internals from a barrel to make the graph look connected.
- Counting an `index.*` barrel re-export as consumption.
Unless:
- The repository has no design root (self-scoping).
- Test files (`*.test.*`, `*.spec.*`) and vendored/build directories are never scanned.
- Token/foundation values and `index.*` barrels are not judged.
- Only capitalized (component) exports are judged.
Why: Unused components still have to be maintained, themed, and migrated; a design system grows by adjudication, not by accretion of pieces nobody uses.
