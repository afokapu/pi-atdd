Title: Declare behaviour in htmx markup with hx-on/hx-trigger, not inline on<event> handlers
Given: A non-test file of any kind (HTML, template, JSX, …) contains at least one `hx-` attribute
When: You add or change element behaviour in that file
Then: Use no lowercase inline handler (`on<event>="…"`, e.g. onclick/onsubmit/onchange); declare behaviour with `hx-on` or `hx-trigger`.
Prefer:
- `<button hx-get="/rows/1" hx-on::after-request="track('open')">Open</button>` instead of `<button hx-get="/rows/1" onclick="track('open')">Open</button>` (dies on swap).
- `hx-on` for element-scoped behaviour, `hx-trigger` for the request itself; both survive swaps because htmx re-processes new content.
- Presentational, non-request behaviour: a delegated listener on a stable ancestor that is never swapped.
Avoid:
- Any lowercase `on<event>="…"` (onclick, onsubmit, onchange, …) in htmx-driven markup.
- Mixing the two models: each inline handler is behaviour invisible to the hypermedia lifecycle; they accumulate and drift the codebase back to a JS layer.
Unless:
- The file contains no `hx-` attribute (self-scoping; never scanned).
- React/JSX camelCase props (`onClick={…}`, `onSubmit={…}`): different mechanism, out of scope. Only these props are exempt, not JSX files as such.
- Test files (`*.test.*`, `*.spec.*`).
Why: Swapping an element destroys its inline handler and any closed-over state; conversely a swapped-OUT element's handler can stay live on a detached node, firing stale clicks on markup the user can no longer see. hx-on/hx-trigger join htmx's event and swap lifecycle.
