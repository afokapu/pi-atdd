Title: Token and foundation files hold values, not behaviour
Given: A code file in the `tokens` or `foundations` layer beneath a design root (`design`, `design_system`, `design-system`)
When: The file exists in the repository and the design-system validator scans it
Then: The file contains only values (palette, spacing, radii, motion, scales) and does not import a renderer (`hono/jsx`, `react`, `preact`, `@kitajs/html`), render markup, or branch with `if`/`for`/`while`/`switch`.
Prefer:
- Keep tokens/foundations value-only; move markup to primitives/components and behaviour to the layer that owns it
- During GREEN: leave the value in the token or foundation file
- During GREEN: move only the markup or logic the current behaviour requires to the nearest existing owning layer
- During GREEN: reuse an existing primitive or component before creating a new one
Avoid:
- Moving behaviour into a different layer merely to silence the rule
- Reorganizing unrelated tokens
- Creating a generalized component unrelated to the current acceptance
Unless:
- Test files (`*.test.*`, `*.spec.*`) and vendored/build directories are never scanned
- `.css` token files are values by construction and are not scanned
- A repository with no design root is not judged (self-scoping)
Why: Tokens are what every other layer depends on; once they render or decide, the bottom of the hierarchy has behaviour and every primitive inherits it.
