Title: Read every provided appendix before planning from it
Given: The user's input includes an appendix (file path, file URL, or 'appendix:' mention).
When: You are about to create a planning output (wagon, WMBT, acceptance, feature, component) or to ask what the user wants to create.
Then: Read the appendix with the Read tool and grasp what it shows (multi-screen flow, single component, architecture, etc.) before producing the output or the question.
Prefer:
- Read PNG, JPG, SVG, PDF, audio and video directly as multimodal input.
- Analyze by type: mockup → UI components, layouts, flows, states, interactions, responsive variants; spreadsheet → business rules, calculations, data models, validation constraints; document → requirements, constraints, specifications, acceptance criteria; diagram → architecture, entities, sequences, state transitions, relationships; audio → transcribe, extract user pain points, requirements, context, clarifications; video → workflows, interactions, pain points, existing behavior patterns.
- Enrichment map when creating: wagon → more accurate description, domain model from diagrams/docs; WMBT → better when/must/then from flows/interactions; acceptance → harness (mockup→visual, diagram→integration); feature → component clustering from mockup sections; component → props/state/behavior from mockups and diagrams.
- Grounded question shape: 'I see your mockup shows a login form - are you creating a wagon or adding a feature?'
Avoid:
- Planning from the text request alone, ignoring a provided appendix.
- When creating: producing an output not enriched with the appendix's type-specific content (prefer[1], prefer[2]). Required.
- When creating: leaving the appendix unreferenced in the output's manifest. Required step; manifest structure is defined by the schema, not this convention.
- When intent is unclear (no 'wagon', 'wmbt', etc.): asking an abstract question that ignores the appendix, e.g. 'What do you want to build?' The question must cite what the appendix shows.
Why: Appendices only reduce ambiguity if consumed — to enrich generated artifacts and to ground routing questions in concrete content, cutting confusion and back-and-forth.
