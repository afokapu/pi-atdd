Title: Map artifact names to REST endpoints via the endpoint pattern
Given: An artifact named `{domain}:{resource}[.{category}]` is exposed to external consumers over a REST API
When: its artifact-to-REST endpoint mapping is specified or changed
Then: Map the artifact name to an endpoint following `/{domain}s/{id}/{resource}[/{category}]`, with category facets adding path segments.
Prefer:
- Pluralize the domain segment (`ux`→`/uxs`, `match`→`/matches`, `session`→`/sessions`, `player`→`/players`).
- Turn each category facet into an extra path segment (`ux:foundations` → `GET /uxs/{id}/foundations`; `ux:foundations.colors` → `GET /uxs/{id}/foundations/colors`; `match:result` → `GET /matches/{id}/result`).
- Follow the source's shorter forms where they apply: `session:new` → `POST /sessions` (collection, no `{id}` or resource segment); `player:identity` → `GET /players/{id}` (no resource segment).
- Select the HTTP verb from the resource keyword (creation→POST, read→GET, mutation→PUT, removal→DELETE): POST new/created/registered/started; GET result/active/config/events/foundations; PUT updated/closed/completed; DELETE terminated/deleted.
Avoid:
- Hand-crafting paths that drop the plural domain or the category segments, or otherwise diverge from the pattern beyond the source's own `session:new` and `player:identity` forms.
- Choosing a verb that contradicts the resource keyword, e.g. mapping `session:closed` to POST (closed → PUT, not POST).
Why: A deterministic artifact-to-REST mapping lets external consumers address wagon artifacts over HTTP, and choosing the verb from the resource keyword keeps the API surface consistent with the artifact's lifecycle semantics.
