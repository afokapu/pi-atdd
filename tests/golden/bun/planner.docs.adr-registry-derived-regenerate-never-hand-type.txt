Title: Produce ADR registry entries by regenerating from :decides: edges, never by hand
Given: A docs corpus whose decisions directory holds ADR files, and a registry decisions/index.adoc that exists or must be created
When: You plan or author a change that would alter the registry's ADR entries, including ADR adds, renames or removals and :adr-id: or :decides: edits
Then: Produce the registry entries by regenerating them from the ADR files and their :decides: edges. Never type them by hand.
Prefer:
- Regenerate rather than edit: run `atdd-bun docs adr-register`, which rewrites the adr-register region.
- Add `// BEGIN GENERATED: adr-register` and `// END GENERATED: adr-register` markers in decisions/index.adoc where the list belongs. The generator writes only between them, one line per ADR keyed by `:adr-id:`, from the same documents the check reads.
Avoid:
- Typing an entry into `decisions/index.adoc`. If you find yourself doing that, the entry belongs in an ADR file with a `:decides:` attribute instead.
- Writing decision content into the registry. It holds references to the decisions, never the decisions themselves.
Why: The registry's job is to make the set of ADRs navigable. The moment a human types an entry into it, the set has two sources of truth. A hand-maintained list of decisions drifts from the decisions, which is precisely the failure class ATDD exists to kill, reproduced inside the documentation system itself. Deriving the registry makes drift impossible rather than detectable. The registry is a projection, never a typed list (spec 2 §5.2, §6).
