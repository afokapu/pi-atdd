Title: Keep each feature at 8 components or fewer; split it otherwise
Given: A planner is defining or extending a feature and its list of components.
When: The feature's component count would reach more than 8.
Then: Keep the feature at ≤ 8 components; if more components are needed, split the feature into smaller features instead of exceeding 8.
Prefer:
- Use the typical 8-component budget as a guide: about 2 frontend (presentation + application), 3 backend (application + domain + integration) and 3 shared cross-cutting components.
- When a 9th component is needed, split the feature along a cohesive boundary into separate features, each within the limit.
Avoid:
- Planning a feature with more than 8 components (e.g. 12) and letting it sprawl instead of splitting.
- Gaming the count by merging unrelated responsibilities into one component or hiding components outside the feature just to stay at 8.
Why: A hard ceiling of 8 components keeps features cohesive and bounded, mirroring the WMBT acceptance limits; more than 8 signals the feature is too large and should be split.
