Title: Start journeys from the reference strategy; justify alternatives
Given: A plan defines or revises a journey's execution strategy; strategies are candidate ways to meet declared behavioral obligations.
When: The planner selects, changes or combines strategies.
Then: Begin with the reference strategy, then consider alternatives or combinations only when latency, throughput, cost, reliability, determinism or complexity requirements, or measured workloads, justify their complexity.
Prefer:
- Treat strategies as orthogonal, combinable candidates; none is universally best. The baseline is the reference strategy convention (planner.journey.strategy.reference).
- Keep ownership: interlockings select guarded alternatives, journeys compose control flow, trains stay linear, wagons optimize internals.
- Plan only behavior the plan and runtime actually support; preserve contracts, artifacts, prerequisites, side effects, error paths and terminal outcomes.
- Prove equivalence with behavioral tests; back performance claims with reproducible benchmarks.
Avoid:
- Exploring alternatives without a requirement or measured workload that justifies the complexity.
- Using a strategy choice to bypass interlockings, trains, continuations or acceptances.
- Assuming fork/join, stream or speculation exists; missing capability needs separate implementation and accepted proof.
- Slipping observable behavior changes in via a strategy; they need their own accepted route.
Why: Alternatives add complexity and risk to behavior that must stay equivalent. This is Bun-owned advisory planner guidance, not a new runtime mode or independently enforced rule; existing journey, interlocking and acceptance validators stay authoritative.
