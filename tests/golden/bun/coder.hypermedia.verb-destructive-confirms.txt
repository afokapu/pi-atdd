Title: Destructive htmx requests declare a confirmation
Given: A markup element carrying `hx-delete` (newly added or already existing)
When: the markup is written, changed or checked
Then: The same opening tag that carries `hx-delete` MUST also carry `hx-confirm="…"` (yes/no gate) or `hx-prompt="…"` (typed-input gate).
Prefer:
- `<button hx-delete="/orders/7" hx-confirm="Delete order 7?">Delete</button>`.
- For high-value deletions use `hx-prompt` so the user types something meaningful rather than reflexively clicking OK (confirm vs prompt is a product decision on friction).
- Express destructive requests with `hx-delete` so the guard is checkable.
Avoid:
- `<button hx-delete="/orders/7">Delete</button>` (unguarded).
- Confirmation on a neighbouring control or elsewhere in the file — protects nothing.
- A delete as `hx-post` to a `/…/delete` route, hiding the verb from this rule.
- Suppressing, waiving or baselining the finding: this rule is `strict` (severity 2) — an unguarded delete is not suppressible; add the confirmation instead.
Unless:
- An element carrying `hx-prompt` instead of `hx-confirm` satisfies the rule.
Why: In hypermedia a delete is one attribute on a clickable element: no form submit, route transition or framework guard sits between click and request. htmx removes the handler where confirmation used to live, so it must be relocated onto the element as declarative `hx-confirm`, or it is lost in the migration.
