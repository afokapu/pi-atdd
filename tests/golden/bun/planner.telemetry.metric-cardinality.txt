Title: Keep high-cardinality identifiers out of metric labels
Given: A telemetry tracking plan contains a metric item (new, edited or existing).
When: You declare or review the metric's dimensions (labels).
Then: Every dimension declares a cardinality of low or medium; none is declared high and none names a property the item declares cardinality high.
Prefer:
- Keep the identifier, change the signal: label the metric with bounded dimensions (e.g. an outcome, cardinality low) and carry the identifier as an event, log or trace property declared cardinality high — for example on the sibling event's properties. If the identifier is already carried by such a property, removing it from the metric dimensions is enough.
- Treat any property whose distinct-value volume is unbounded or near-unbounded (request ids, user ids, session tokens) as a high-cardinality identifier and carry it as an event, log or trace property, where cardinality is the point rather than a liability.
- To check a dimension, compare its name with the item's declared properties; if a property of that name is declared cardinality high, the dimension is rejected.
Avoid:
- Dropping the identifier from the plan entirely instead of carrying it as an event/log/trace property.
- Leaving a metric dimension's cardinality undeclared, or relabelling a high-cardinality id as low/medium to pass the check.
Unless:
- Event, log and trace properties may declare cardinality high where justified; this rule judges metric dimensions only.
Why: Every distinct metric-label value becomes a new time series, so a high-cardinality label is a backend outage with a YAML file attached; the plan is where that mistake is cheapest to catch.
