Title: GREEN: smallest legal implementation of the failing acceptance
Given: a governed ATDD Bun task whose current behavioral acceptance is still RED
When: you write implementation code to make that acceptance pass
Then: Write the smallest correct implementation that makes the current failing behavioral acceptance pass while respecting every active construction constraint.
Prefer:
- Start from one failing behavioral acceptance. Keep the search on the missing behavior, and prefer a naturally simple implementation.
- Reuse the nearest existing compliant contracts, components, dependencies and patterns. Implement the smallest path that makes the required behavior pass.
- Add a new boundary or abstraction only when the current behavior actually needs it, that is, when no existing compliant path can express it.
- Derive traceability metadata from the plan and the acceptance. Do not invent it.
- Treat the rules from atdd_topology, bun_green_traceability_detector, bun_clean_architecture_detector, bun_fullstack_detector, bun_design_system_detector and bun_responsive_detector as limits on a legal GREEN. These cover traceability/topology, architecture/dependency direction, runtime, design-system and responsive. Other active profiles, especially tester, traceability and security, are equally binding.
- `green-*` rules are a traceability family (implementation identity, proof, runtime, purpose, side, layer), not a phase. Leave them where they are. They constrain GREEN.
- The seven metrics sensors may run at any time, even while the acceptance is RED, and they stay strict. Only your response changes with the phase.
- Stop expanding scope once the acceptance passes and the construction constraints are satisfied.
Avoid:
- Knowingly violating a construction constraint and planning to repair it later.
- While RED: broadening the implementation just to optimize a quality metric, or gaming any finding.
- While behavior is still being discovered: redesigning adjacent systems, generalizing for hypothetical callers, or doing unrelated cleanup.
- Writing deliberately poor code. GREEN does not permit it.
- Treating behavioral GREEN as the end of the coding loop.
Unless:
- A narrow structural change may come before behavioral GREEN when the existing design makes the required behavior impossible to implement correctly. Preserve already-proven behavior and change only the verified blocker.
Why: GREEN and REFACTOR are different search problems, and splitting them does not change enforcement. GREEN finds the smallest legal implementation of the required behavior. Construction constraints define what counts as legal while behavior is being discovered.
