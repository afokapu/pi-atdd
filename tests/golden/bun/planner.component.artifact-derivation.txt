Title: Derive component names from the artifact resource plus a capability suffix
Given: A planned component handles an artifact whose resource (the part after the colon) and type are known, even if the full URN is not yet final.
When: The planner names the component or writes its component URN.
Then: Name the component as the PascalCase artifact resource plus a capability suffix chosen by artifact type and the component's responsibility.
Prefer:
- PascalCase the resource first (player-wallet→PlayerWallet), then append the suffix.
- Suffix catalogs: events (past tense) Publisher/Emitter/Broadcaster; states (adjective) Tracker/Monitor/Manager; data (noun) Provider/Handler/Processor/Maker; configs Configurator/Builder/Initializer.
- Source examples use an artifact-derived stem that qualifies or replaces the literal resource: match:started→MatchStartedPublisher, wallet:credited→WalletCreditedEmitter, timebank.remaining→TimebankTracker, session:active→SessionManager, match:config→MatchConfigurator, league:config→LeagueBuilder. The source does not reconcile these with the literal rule; keep any stem traceable to the artifact.
- One artifact may fan out to several components across sides/layers; the source's worked example also uses responsibility suffixes outside the catalogs: ChoiceDisplay (presentation UI), ChoiceValidator (validation), ChoicePersister (persistence), alongside ChoiceMaker.
- Let the name describe the CAPABILITY to handle the artifact.
Avoid:
- Non-PascalCase names (e.g. 'choiceHandler').
- A suffix unrelated to the artifact type.
- Names not traceable to the handled artifact.
Why: Mechanical derivation from the artifact resource keeps component names predictable and traceable to the artifact they handle, while the type-driven suffix encodes the component's capability.
