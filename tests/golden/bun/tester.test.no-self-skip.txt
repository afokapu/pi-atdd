Title: Do not let a test disable itself; exclude it at the runner level instead
Given: A test case (it / test / describe) exists in a test suite
When: the test is disabled from inside its own source — a `.skip` / `.todo` / `.failing` modifier or an early `return` guarded on an environment check
Then: Remove the self-disabling so the test actually runs (or delete the test); if it must not run somewhere, exclude it in the runner's configuration instead.
Prefer:
- Remove the modifier and let the test run, or delete the test.
- Exclude via a runner config filter: visible in configuration, not invisible in a green suite.
Avoid:
- `.skip` / `.todo` on it / test / describe.
- `if (!process.env.X) return` in a test body: same fault in disguise, more common, silent exactly where nobody watches.
- `.failing` as a disabler. Source conflict: statement forbids it; self_skip term exempts `.fails`/`.failing` as core RED markers. Escalate, don't decide.
Unless:
- Skip in a fixture/helper that is not itself a test case.
- Runner-level exclusion (config filter), the supported way not to run a test.
Why: A skipped test reports GREEN: the suite passes, the gate sees no failure, and the acceptance is recorded as covered by a test that did not run.
