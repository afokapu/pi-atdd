Title: Compose design-system primitives for interactive controls in app code
Given: App code outside a design root (design/design_system/design-system): .tsx/.jsx, or .ts/.mts HTML in string/template/tagged-template literals (htmx/Bun shape).
When: It renders an interactive control.
Then: Render it through a design-system primitive, never a raw lowercase <button>, <input>, <select>, or <textarea>.
Prefer:
- Use the existing primitive; pass required htmx/DOM attributes through it.
- During GREEN: reuse the primitive that already represents the control.
- During GREEN: extend only the smallest prop/attribute surface the current interaction requires.
- During GREEN: create a new primitive only if none represents the control correctly.
Avoid:
- Raw interactive markup bypassing the primitive just to pass the acceptance.
- Generic primitive props the current behavior does not need.
- Restyling or migrating unrelated controls.
Unless:
- No design root in the repo (nothing to connect to yet; not judged).
- The design system's own primitives.
- Test files (*.test.*, *.spec.*) or vendored/build directories.
- Plain .html templates (cannot import components).
Why: Controls hold focus, disabled, error and loading states; each raw control re-implements them and diverges. Primitives keep controls themed, accessible, consistent.
