Title: Name appendix files {artifact-name}_{type}_{filename}
Given: A planning artifact (for example a wagon, WMBT, feature or component) has, or needs, a supporting appendix file, regardless of where that file is stored.
When: The planner creates, renames or references that appendix file, or edits or reviews an existing appendix whose filename does not follow the pattern.
Then: Name the file {artifact-name}_{type}_{filename}: the owning artifact's name first, one of the six recognized appendix types second, a descriptive filename last, separated by underscores.
Prefer:
- Use the owning artifact's exact name/id as the first segment (e.g. wagon slug, WMBT id like E023, feature slug, component name).
- Take {type} only from the six recognized appendix types listed in planner.appendix.types (e.g. mockup, diagram, spreadsheet); look the list up there rather than guessing.
- Make {filename} descriptive of the content (e.g. overview, sequence, tax-rules, states); hyphens are fine inside a segment.
- When editing, reviewing or referencing an existing misnamed appendix, rename it to the pattern and update references to the new name.
Avoid:
- Bare filenames missing the {artifact-name} and {type} segments (e.g. overview.png).
- Hyphens instead of underscores as segment separators (e.g. checkout-flow-mockup-overview.png).
- Inventing a {type} value outside the six recognized appendix types.
Why: Encoding the owning artifact and appendix type in the filename ensures uniqueness, traceability back to the artifact, and clear type identification without opening the file.
