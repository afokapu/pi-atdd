Title: Derive components from the feature's ioSeeds and WMBT verbs
Given: A feature's components are being planned, whatever ioSeeds (consume/produce) or WMBTs the feature currently has, including none
When: the planner generates, adds or re-derives that feature's components
Then: Derive each component from a concrete ioSeed trigger or WMBT verb in the feature, with the business capability and layer the derivation map gives that trigger.
Prefer:
- Steps: analyze ioSeeds/WMBTs → identify needed capabilities → assign layers → generate up to 8 components with complete structure → confirm all feature needs are covered.
- ioSeeds map: produce event:*/notification:* → event publishing (application|integration); consume event:*/notification:* → event handling (application|integration); consume command:* → command processing (application); produce query:* → query handling (application|domain).
- WMBT verbs map: validate/verify/check → validator (domain); process/compute/calculate → processor (application|domain); display/show/render → display (presentation); store/save/persist → persister (integration); coordinate/orchestrate/manage → coordinator (application).
- Examples: WMBT 'persist choice' → ChoicePersister at integration; ioSeeds.consume has command:* → command-processing component at application.
- Where the map allows two layers (a|b), either listed layer complies; the source gives no tie-breaker, so record which trigger justified the chosen layer.
- If the feature has neither ioSeeds nor WMBTs, or covering every trigger would need more than 8 components, report that conflict instead of inventing components, exceeding the cap or silently dropping coverage.
Avoid:
- Inventing a component with no ioSeed or WMBT trigger behind it.
- More than 8 components for one feature.
- Leaving an ioSeed trigger or WMBT need uncovered.
Why: Deriving components from ioSeeds and WMBTs keeps generation systematic and traceable: every component exists because a concrete trigger in the feature called for it.
