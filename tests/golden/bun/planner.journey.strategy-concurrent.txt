Title: Plan concurrent journey branches only with explicit fan-out, release, join and failure semantics
Given: A plan introduces or changes concurrency: parallel journey branches or within-wagon concurrency, or its evidence
When: the planner authors the topology, wagons, acceptances or docs for it
Then: Plan branches as concurrent only if the topology explicitly specifies fan-out, dependency release, join, and failure semantics; otherwise keep them sequential.
Prefer:
- Concurrency only for independent expensive operations whose measured saving exceeds its overhead.
- Prove bounded concurrency, prerequisite satisfaction, joining, cancellation, failures and result equivalence; benchmark latency.
Avoid:
- Treating multiple incoming continuations as a join.
- More than one outgoing continuation or terminal per route; assuming journeys give fork/join.
- Cross-interlocking fan-out/fan-in (not yet supported).
- Inferring unimplemented orchestration or a new runtime dispatch option from this pattern.
Why: Journeys allow one continuation or terminal per route and lack fork/join, so unspecified parallelism is unsynchronized and unverifiable. Within-wagon concurrency can honor existing contracts.
