Title: Commons domain modules import nothing outward
Given: A source module under a `commons/domain/` or `shared/domain/` tree
When: it has an import resolving into the commons `application/` or `integration/` layer
Then: Remove the outward import: commons domain MUST NOT import application or integration code; dependencies point inward only.
Prefer:
- Move genuinely domain-owned data or behavior into domain.
- Invert an outer capability behind a domain-facing port.
- During GREEN: prefer existing domain types, functions, and ports; introduce a new port only when the current behavior requires the domain to request an outer capability, and keep it as narrow as the acceptance requires.
Avoid:
- Importing outward as a temporary shortcut.
- Moving unrelated application or integration behavior into domain.
- Inventing a future-proof abstraction.
Unless:
- Test files and vendored/build directories are never scanned.
- Bare npm specifiers resolve outside the project graph and are not layer-checked.
- A file with no layer segment is outside the rule, not in violation.
Why: The domain is the centre holding the rules and must not know what orchestrates or transports them; an outward import makes the rules unusable without the machinery, first seen as a domain test needing a database.
