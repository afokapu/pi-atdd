Title: Reconcile delivered behavior with declared intent before accepting a delivery
Given: A delivery whose deterministic CI and convention gates are green is offered for final acceptance
When: the final reviewer decides whether to accept it
Then: Produce a durable APPROVE, RETURN or ESCALATE decision on whether the delivered behavior of the assembled system is the intended behavior.
Prefer:
- Intent first: before relying on diff or implementation, read the acceptance criteria, wagon responsibilities, train sequence, interlocking route decisions, exposed journey and delivery criteria when available; state the externally meaningful behavior that should be observable if the delivery is correct.
- Choose the highest meaningful assembled boundary: the real user-facing journey for human-facing behavior, the exposed assembled boundary for API/runtime behavior, the production interlocking and train path when routing is material.
- Exercise the real production path (see unless[1]) with the minimum inputs needed; observe user-visible outcomes, API responses, persisted effects, emitted events, route selection plus its business outcome, or other effects the plan names.
- Reconcile three sources independently; all must materially agree: (1) declared intent: what plan and delivery criteria require; (2) executable proof: what acceptance, smoke, route, train and journey tests actually prove; (3) observed runtime: what the assembled system does through the real boundary. No single source suffices: passing tests alone are insufficient because a test may have drifted with the implementation; observed runtime alone is insufficient if it no longer satisfies declared intent; a correct plan whose implementation is unexercised or unreachable is also incomplete.
- Look for: missing required behavior; intended behavior unreachable through the assembled app; materially unexpected new behavior; interlocking selecting the wrong train; a train sequence yielding a different business outcome; a journey's final user-visible result differing from intent; passing tests proving a different behavior than the plan; acceptance/planning artifacts silently changed to match the implementation without authorized intent change.
- Inspect diff and implementation only after expected behavior is set, to explain discrepancies, understand risk, or judge whether an observation is trustworthy.
- APPROVE only when intent, proof and runtime materially agree, required behavior is reachable through the assembled system, and no material unintended behavior was found in reviewed scope. RETURN with the concrete behavioral discrepancy and evidence when behavior is missing, wrong, unreachable, materially contradicted, or proof does not match intent. ESCALATE when intent is ambiguous/contradictory or the observed need requires changing agreed product behavior.
- When remediating a deficient review, re-run final review outside-in: Intent, Exercise, Observe, Reconcile, Decide.
Avoid:
- Starting final review while required CI, tests, type, security or active strict convention checks fail; return the failing gate to the responsible implementation phase before spending semantic-review reasoning.
- Deriving expected behavior from the PR diff, implementation or a test body: they show what was built, not what was supposed to be built.
- Treating passing tests, a clean diff, green CI or green convention checks as the final behavioral judgment; they are supporting evidence only. Treating a passing E2E test as proof without checking what it proves.
- Moving inward to an internal function because it is easier to invoke; accepting internal calls, implementation objects, mocks or descriptive tokens instead of the declared observable result.
- Reviewing only the lines changed in the PR.
- Reopening naming, decomposition, abstraction, complexity, formatting or other design/style/refactoring questions that passed their governing phase, without concrete evidence of a behavioral defect or delivery risk.
- Silently redefining or changing the plan to make the implementation appear correct; using final review to expand scope or redesign.
- Approving from static inspection alone when the claim requires runtime observation.
- Accepting or approving a delivery despite a material mismatch: a material mismatch blocks delivery.
Unless:
- A delivery intentionally changing no externally observable behavior still requires reconciliation; the reviewer may set the intended invariant to 'no behavioral change' and verify it with the relevant assembled proofs instead of inventing a new user journey.
- If the behavior cannot be exercised safely against production dependencies, use the highest faithful environment and boundary the plan authorizes; static-only approval is still not allowed when the claim needs runtime observation.
- Ambiguous or contradictory intent is not a reviewer failure and must not be resolved by inference; return ESCALATE so the responsible planning authority settles it.
Why: Tests and implementation can drift from the plan together while still agreeing with each other; only an intent-first, independent comparison of intent, proof and assembled runtime catches missing, unreachable or semantically drifted behavior that green gates cannot see.
