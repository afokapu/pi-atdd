Title: Assert on the returned htmx fragment, not just the status
Given: In a Bun/htmx stack test, a test case performs an actual HTTP request (not a direct handler call) and asserts on the response status or ok
When: the tester writes or changes that test case
Then: The test case MUST also assert on the response BODY; reaching the body in any form (.text(), .json(), a markup matcher) satisfies the rule.
Prefer:
- Assert on the fragment, not just the status line:
  expect(res.status).toBe(200);
  const html = await res.text();
  expect(html).toContain('id="order-1"');   // the id a later oob swap targets
- For htmx fragments, make the body assertion check the fragment contract (hx-attributes, ids later oob swaps target, structure), as in the example above.
Avoid:
- Status-only tests: asserting expect(res.status).toBe(200) or res.ok and stopping — proves the route exists and nothing about what the user will see.
Unless:
- The case does not perform an HTTP request (out of scope).
- The case never asserts on status (out of scope). Note: asserting on res.ok counts as a status assertion, so an ok-only case is in scope.
Why: In a JSON API the contract is the payload and status plus a parsed field is a complete test; in htmx the contract is the markup (hx-attributes, ids later oob swaps target, structure) swapped into the live DOM. A status-only test misses a refactor dropping an id a sibling's hx-swap-oob needs, which fails silently at runtime (see coder.htmx.swap-oob-carries-id).
