Title: Docs-graph resolver: resolve or report, never fabricate a node
Given: The docs-graph resolver that turns .adoc relationship attributes into graph edges.
When: You plan, specify or change how that resolver builds the graph.
Then: The resolver MUST build the declared-id set first, admit an edge only if its target is in that set, and report every other edge as a finding. It must never synthesize a node for an undeclared target and never silently drop the edge.
Prefer:
- Write the acceptance so that it asserts the graph NODE COUNT directly, not merely the finding. An unresolved edge adds no node.
- Also assert that every unresolved edge appears as a reported finding, so that none is silently dropped.
Avoid:
- An ensure-node-on-edge pattern. In `graph_builder.py:215`, `_ensure_node` synthesizes a bare node for any unseen URN, and `add_edge` calls it on BOTH endpoints. So any edge that names a non-existent target conjures that target into being.
Unless:
- Nothing is exempt from the no-fabrication half. There is no configuration that permits synthesis.
- An absent attribute is not an unresolved edge. Only declared relationships are resolved.
Why: Fabrication is worse than absence. An absent parent leaves an orphan, and an orphan check catches it. A fabricated parent makes the node look CONNECTED, which defeats that check. This defect has ALREADY HAPPENED: 147 of 168 containment edges in the repository's other graph hang off invented nodes.
