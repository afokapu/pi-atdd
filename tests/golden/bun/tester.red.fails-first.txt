Title: RED tests carry a guaranteed-fail marker
Given: A bun:test test declaring Phase: RED
When: the RED test is written, edited, or scanned by the RED gate
Then: Each RED test MUST contain at least one accepted guaranteed-fail marker: `throw new Error('Not implemented …')`, `throw new UnimplementedError(…)`, `expect(false).toBe(true)`, `expect(true).toBe(false)`, `expect.fail(…)`, `return Promise.reject(…)`, `it.fails(`, or `test.failing(` (bun:test's spelling of `it.fails(`, accepted identically).
Prefer:
- Write the behavioral oracle first (required by red-behavioral-assertion): derive it from the bound acceptance's Given/When/Then so it fails because the behavior is not implemented correctly.
- Then add one marker after the stimulus runs, e.g. `expect.fail("<behavior> not implemented yet");` or `throw new Error("Not implemented: <behavior>");`.
- Remove the marker in GREEN only once the behavioral assertion carries the proof and passes.
Avoid:
- Using the marker as the only meaningful reason the test is red.
- Throwing before the declared stimulus is exercised.
- Wrapping a vacuous or already-passing case in `it.fails` / `test.failing`.
- Weakening the behavioral assertion because the marker already guarantees failure.
Why: Failing-first is a runtime property no static detector can observe; the marker is the decidable structural proxy. It aids the detector; it is not the RED objective or the behavioral oracle.
