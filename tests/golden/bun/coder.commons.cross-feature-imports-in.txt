Title: Reach sibling commons features only through the layer root
Given: A module inside a commons feature directory `commons/<layer>/<feature>/…`
When: it imports a capability of a sibling commons feature
Then: The import MUST go through the layer root, never directly into the sibling feature's internals.
Prefer:
- Reuse an export that already represents the required capability.
- If the capability is intentionally shared, expose the smallest stable surface from the layer root.
- If it is not a shared responsibility, keep the implementation local instead of reaching across.
Avoid:
- Importing a path inside a sibling commons feature's directory.
- Exporting a sibling's internals wholesale.
- Creating a generic shared module merely to make the import legal.
- Moving unrelated code between features.
Unless:
- Test files and vendored/build directories are never scanned.
- Bare npm specifiers resolve outside the project graph and are not layer-checked.
- A file with no layer segment is outside these rules rather than in violation of them.
Why: A feature's internals are its own; the layer root is the surface it deliberately exposes. Reaching past it couples two features through a path neither chose to publish, which is how a shared module quietly becomes unsplittable.
